# 06 — Engines (Learning Engine Layer)

This file describes the **implementation contracts** of engines that provide algorithms to the Capability Layer (`03-features.md`). They belong to one Learning Engine layer. FSRS, model providers, speech services, and routing logic are implementations inside governed boundaries; none is a separate product authority.

```text
Learning Engine
  ├── FSRS Engine           → implement REVIEW.FSRS
  ├── Evaluation Engine     → implement EVAL.Writing/Speaking/Pronunciation/Examiner
  ├── Recommendation Engine → implement PERSONAL.Recommendation/NextBestAction/Insights
  ├── Quality & Cost Plane  → implement OPS.*
  └── Governance Engine     → implement GOVERNANCE.*
```

## Engine-wide intelligence rule

LenBands is **deterministic-first**.

Before invoking a model/speech provider, an engine must answer:

1. Can typed rules, formulas, state machines, answer keys, SQL, controlled mappings, or a maintained library satisfy the required quality?
2. Can a reusable/precomputed governed result satisfy it?
3. If inference is required, what is the smallest bounded model/specialist operation that solves only the non-deterministic part?
4. Does the operation need escalation to a stronger route because it materially affects assessment integrity or learner outcome?
5. What is the safe state if no approved route is available?

A model/provider response is never authoritative merely because it was generated by AI. It becomes a usable result only after schema, provenance, domain, evidence, and quality validation.

## 1. FSRS Engine (implement `REVIEW.FSRS`)

FSRS (Free Spaced Repetition Scheduler) schedules review for **retrievable review units** such as vocabulary, grammar forms/rules, collocations, sentence patterns, pronunciation targets, and traceable error concepts.

FSRS is **not** the mastery model for complex IELTS constructs.

### Boundary

Use FSRS to answer:

> When should this retrievable unit be reviewed again?

Do not use FSRS maturity to answer:

> Has the learner mastered Writing Coherence, Reading inference, Listening distractor rejection, or Speaking Fluency?

Complex-skill mastery/readiness requires independent performance, transfer, and maintenance evidence under the learner-evidence contract.

### Card model

| Field | Description |
|---|---|
| `card_id`, `user_id` | stable identifiers |
| `content_ref` | versioned link to the review/remediation unit |
| `content_type` | vocabulary/grammar/collocation/pattern/error-concept/pronunciation-target/question-review |
| `due` | next review timestamp |
| `stability` | scheduler stability state |
| `difficulty` | scheduler difficulty state |
| `elapsed_days` | days since last review |
| `scheduled_days` | scheduled interval |
| `reps` | review count |
| `lapses` | forgetting count |
| `state` | New / Learning / Review / Relearning |
| `last_review` | timestamp |
| `source_evidence_ref` | optional evidence/remediation source |
| `scheduler_version` | exact algorithm/config version |

### Review flow

```text
Card due
  ↓
Learner attempts retrieval
  ↓
Reveal/check according to review-unit policy
  ↓
Rating (Again/Hard/Good/Easy)
  ↓
FSRS calculates next scheduler state
  ↓
Persist versioned card state
```

A review success updates review state. It does not automatically create transfer/readiness evidence.

### Card sources

- Vocabulary from Knowledge Assets (`KA.Vocabulary`)
- Collocation (`KA.Collocation`)
- Grammar/remediation unit (`KA.Grammar` or governed error mapping)
- Wrong-question concept from Mistake Notebook when a retrievable unit exists
- Speaking/Writing pattern used as a learning aid, not as proof of free production
- Pronunciation target/drill item

### Optimization

- P0/MVP: use a validated library/default or cohort parameter set; do not optimize per learner with insufficient history.
- Optimization runs offline and is promoted only after holdout validation.
- Per-learner tuning is deferred until sample sufficiency, rollback, version audit, and measurable benefit exist.
- Scheduler tuning must not be conflated with improvement in complex IELTS performance.

### Review Forecast

- forecast due volume over 7/30 days;
- detect overload;
- permit policy adjustment without silently lowering assessment/readiness standards.

## 2. Evaluation Engine (implement `EVAL.*`)

Learner-facing evaluation is **fully automated at runtime**; there is no human examiner dependency in the transaction path. Offline examiner-rated or otherwise qualified reference data may be used for benchmark/calibration when provenance and rights allow it.

The automated evaluator is an engine, **not a role or source of product truth**.

### Score identity boundary

Always preserve:

- `official_ielts_score` — official result supplied by learner/authorized source;
- `exam_simulation_estimate` — LenBands estimate from a governed full simulation;
- `diagnostic_estimate` — partial/task/placement estimate;
- `criterion_evidence` — evidence about a rubric criterion/micro-skill;
- `learning_mastery` / readiness — derived learner-model state.

A Writing Task 2 result alone is a task-scoped diagnostic estimate and must not be rendered as an official IELTS Writing section score.

### Evaluation operation versus result validity

Processing state and result trustworthiness are different dimensions.

```text
operation_state:
  accepted -> processing -> succeeded | delayed | unavailable | failed | cancelled

result_validity:
  accepted | limited_evidence | insufficient_evidence | invalid | integrity_review
```

Do not encode `low_confidence` simultaneously as both transport state and result state.

### Common evaluation pipeline

```text
immutable submission snapshot
  ↓
deterministic validation / cheap features
  ↓
scorer route version
  ↓
minimum required model/speech operation(s)
  ↓
structured output normalization
  ↓
rubric/evidence validation
  ↓
uncertainty / disagreement / integrity policy
  ↓
optional escalation only when justified
  ↓
immutable governed result
  ↓
deterministic remediation mapping
  ↓
optional natural-language explanation
```

### Writing pipeline

Writing must not spend a large-model call on work that code can do exactly.

```text
Essay + task snapshot
  ↓
Deterministic pre-check
  - task identity/version
  - word count
  - language/input validity
  - empty/off-topic/duplicate obvious guards where reliable
  ↓
Benchmark-approved primary rubric scorer
  - Task Response / Task Achievement when applicable
  - Coherence & Cohesion
  - Lexical Resource
  - Grammatical Range & Accuracy
  ↓
Evidence/schema validator
  - every material claim references text evidence or explicit task-level rationale
  - score scope preserved
  ↓
Uncertainty/disagreement gate
  ├─ routine valid case -> accept
  └─ hard/high-risk case -> stronger independent approved route
  ↓
Immutable diagnostic result
  ↓
Error/remediation mapping from controlled IDs
  ↓
Quick/Standard/Deep feedback rendering
```

Rules:

- stronger/expensive scoring is escalation, not default;
- second pass runs only when uncertainty/risk policy justifies its marginal cost;
- feedback generation must not change the already-governed score;
- reusable explanations/examples should be precomputed/versioned where possible;
- rewriting is optional coaching and must not be confused with evidence that the learner can independently produce the improved text.

### Speaking pipeline

Speaking is a staged evidence pipeline, not one black-box multimodal score.

```text
Audio + prompt/part snapshot
  ↓
Audio quality / duration / integrity gate
  ↓
STT transcript
  ├─ deterministic/derived timing features where valid
  │   - speech rate
  │   - pause patterns
  │   - repetitions/repairs
  ├─ lexical/grammar evidence extraction
  └─ specialist acoustic/pronunciation evidence when required
  ↓
Rubric scorer
  - Fluency & Coherence
  - Lexical Resource
  - Grammatical Range & Accuracy
  - Pronunciation
  ↓
Evidence aggregator + validity gate
  ↓
Optional escalation for hard/high-risk case
  ↓
Immutable scoped result + feedback actions
```

A general-purpose LLM must not be the sole measurement mechanism for phoneme accuracy, stress, timing, or intonation when specialist speech/acoustic evidence is required by the pronunciation contract.

### Examiner boundary

`EVAL.Examiner` generates/chooses appropriate Speaking follow-up questions under an explicit conversation state machine. It is separate from `EVAL.Speaking` scoring.

The question-generating context must not silently alter rubric scoring policy. Scoring receives the governed prompt/question/answer history required by its scorer contract, not an unrestricted agent memory.

### Pronunciation pipeline

Use specialist speech/acoustic mechanisms for measurable pronunciation evidence, then optionally use a language model/template to explain results.

```text
Audio
  -> signal/audio-quality gate
  -> alignment/acoustic/speech features
  -> pronunciation evidence
  -> governed pronunciation interpretation
  -> explanation/drill recommendation
```

### Band prediction

`EVAL.BandPrediction` is derived from admissible historical evidence with explicit scope and uncertainty. A model is not required when deterministic/validated aggregation satisfies the prediction contract.

Prediction must reason about evidence coverage, independence, recency, task/module coverage, and uncertainty; it must not average arbitrary task-level numbers into false precision.

### Context minimization

Model-assisted coaching/scoring receives a **bounded relevant context**, not the learner's entire history.

```yaml
learner_state_snapshot:
  target_profile_ref: ...
  current_task_ref: ...
  relevant_constructs: []
  relevant_recent_evidence_refs: []
  top_recurring_error_ids: []
  current_intervention_ref: ...
  exposure_or_novelty_state: ...
```

Raw history is included only when explicitly required by the operation and privacy contract.

### Evaluation result contract

Every governed result records at least:

| Field | Purpose |
|---|---|
| `score_scope` | task/criterion/section/simulation scope |
| `rubric_version` | rubric authority used |
| `task_version` | immutable elicitation context |
| `scorer_route_version` | governed route identity |
| `model/provider provenance` | reproducibility/audit metadata permitted by policy |
| `prompt_or_config_hash` | reproduce route behavior without logging raw private prompt/content |
| `result_validity` | accepted/limited/insufficient/invalid/integrity_review |
| `evidence` | sentence/audio segment/feature supporting material judgments |
| `feedback_actions` | governed remediation candidates |
| `quality_flags` | audio/input/integrity/coverage flags |
| `cost_metadata` | route tier, tokens/audio units, retries/escalation, latency |

Only admissible accepted results feed readiness as ordinary evidence. Limited/insufficient/integrity-review results follow their explicit evidence-admission policy.

### Learner-facing uncertainty

Raw model confidence is governance telemetry unless empirically calibrated for a learner-facing interpretation.

Do not show a scientific-looking percentage such as `73% confidence` by default. Prefer validated language such as:

- `limited evidence`;
- `provisional estimate`;
- `more evidence required`;
- `result unavailable — please retry/resubmit`.

### Failure Contract

Failure is product behavior, not merely a technical log. Engines return the common governed failure envelope; concrete P0 failure codes remain owned by `artifacts/engineering/contracts/runtime/failure-taxonomy-contract.md`.

```json
{
  "failure_code": "EVAL_TIMEOUT",
  "failure_version": "1.0.0",
  "source": "transcription|scoring|recommendation|sync|quota",
  "severity": "recoverable|degraded|terminal",
  "retryable": true,
  "retry_after_seconds": 30,
  "user_state": "processing|delayed|unavailable|action_required",
  "data_action": "preserve|discard_invalid|await_sync",
  "fallback": "queue_retry|basic_result|save_draft|none",
  "quota_effect": "charged|not_charged|reserved_released",
  "telemetry_event": "evaluation_failed",
  "trace_id": "id"
}
```

Failure rules:

- retry has one owning layer, bounded attempts, backoff, idempotency and deadline;
- never charge twice for internal retry of one learner operation;
- preserve learner-created data before fallback;
- provider errors/trace IDs never replace actionable learner guidance;
- scoring fallback is allowed only to benchmark-approved routes preserving score semantics;
- if no approved scorer exists, preserve the submission and report delayed/unavailable rather than silently lower quality.

### Assessment integrity / anti-gaming

`GOVERNANCE.AntiGaming` is an integrity-risk system, not a cheating oracle.

Prefer stronger, auditable signals:

1. known sample/corpus similarity;
2. copied-task/passage overlap where relevant;
3. item/prompt exposure and prior-answer familiarity;
4. repeated/template similarity across attempts;
5. impossible/inconsistent interaction provenance when reliably measurable;
6. model-generated-text detector only as an optional weak signal, never sole adjudicator.

A detector output must not automatically label a learner as cheating or permanently corrupt normal history. Policy requires false-positive monitoring, neutral explanation, resubmission/retest path, and explicit evidence-admission behavior.

## 3. Recommendation Engine (implement `PERSONAL.*`)

The Recommendation Engine turns governed learner evidence into candidate actions. **It does not ask an LLM to decide the learning path from raw history.**

### Learner state inputs

At minimum:

- target profile/module and exam relevance;
- assessment history with evidence scope/validity;
- construct uncertainty and evidence counts;
- independent/transfer/maintenance state;
- review due state;
- item/content exposure/novelty;
- current intervention and recent recurrence;
- available time/energy and recent workload;
- content eligibility/rights/calibration state.

### P0 deterministic selection

P0 should remain auditable and deterministic unless evidence proves a model-based selector adds material value.

```text
admissible learner evidence
  ↓
derive gaps + under-measured constructs
  ↓
generate eligible candidate actions
  ↓
apply hard constraints
  - content available/published
  - prerequisite/state
  - exposure/novelty
  - time/energy
  - entitlement
  - due review / exam relevance
  ↓
multi-objective rank
  - learning value
  - evidence value / uncertainty reduction
  - transfer need
  - goal relevance
  - recurrence
  - workload
  ↓
choose one primary action + lighter alternative
  ↓
render deterministic reason
  ↓
optional model-assisted wording only if needed
```

### Why weakness-only routing is insufficient

The selector must balance exploitation and exploration:

- **exploit** a well-supported weakness;
- **explore** under-measured constructs to reduce uncertainty;
- preserve syllabus/construct coverage;
- avoid repeated familiar items creating fake confidence;
- respect review due state and transfer needs;
- avoid overload.

### Outputs

| Capability | Contract |
|---|---|
| `PERSONAL.NextBestAction` | one high-value eligible action + reason + lighter alternative |
| `PERSONAL.Insights` | derived fact/pattern from governed evidence; natural-language rendering is secondary |
| `PERSONAL.AdaptivePlan` | versioned plan adjustment from learner state and constraints |
| `PERSONAL.WeaknessPractice` | eligible practice selected from supported weakness/evidence need |
| `PERSONAL.GapAnalysis` | target-vs-evidence gap including uncertainty/insufficiency, not only a numeric band difference |

### Insight generation

Facts first, prose second:

```text
governed attempts/tags/evidence
  ↓
deterministic aggregation
  ↓
pattern + confidence/coverage checks
  ↓
structured insight fact
  ↓
template rendering
  ↓ optional
LLM wording if a template is insufficient
```

Never let generated prose become the stored analytical truth.

### Cold start

- use self-report + placement + curated baseline;
- represent uncertainty explicitly;
- do not pretend deep personalization exists before evidence exists;
- when evidence is insufficient, recommend evidence collection rather than inventing a weakness.

## 4. Quality & Cost Control Plane (implement `OPS.*`)

This plane operates across Evaluation, Recommendation, Review, Content, and Experience.

## Execution/routing ladder

```text
Request
  ↓
Deterministic rule/library/SQL
  ↓ insufficient
Versioned precomputed/reusable result
  ↓ insufficient
Small or specialist bounded model
  ↓ high-risk / insufficient quality
Benchmark-approved stronger/specialist route
  ↓ unavailable
Safe degraded state / durable retry
```

A cache is an optimization, not a mandatory tier; runtime-contract rules still require measured justification and a valid invalidation model before enabling product-semantic caches.

### Capability mechanism matrix

| Capability type | Default mechanism | Model escalation |
|---|---|---|
| auth/RBAC/RLS/entitlement | code + Postgres/provider auth | never |
| L/R objective scoring | answer key + normalization | only explanation if needed |
| band arithmetic/score scope | deterministic policy | never |
| FSRS | maintained scheduler library | never for scheduling |
| P0 Next Best Action | deterministic multi-objective rules | only after measured benefit |
| analytics/insights facts | SQL/aggregates | optional wording |
| content schema/rights/publish gates | deterministic validation/workflow | auto-tag suggestion only |
| Writing rubric judgment | benchmark-approved scorer | stronger route for hard cases |
| Speaking rubric judgment | staged speech + scorer pipeline | stronger route for hard cases |
| pronunciation measurement | specialist speech/acoustic model | LLM only for explanation where useful |
| contextual tutor/rewrite | retrieval/template first | bounded generation |

### Quality gates

- **Content**: correctness, taxonomy usefulness, calibration, accessibility, rights.
- **Evaluation**: rubric agreement, criterion/task agreement, stability, evidence quality, uncertainty calibration, drift/bias and reproducibility.
- **Recommendation**: actionability, independent retest/transfer lift, uncertainty reduction, recurrence and overload rate.
- **Experience**: time-to-first-useful-value, recovery success, abandonment, accessibility and notification fatigue.

Do not promote a cheaper model/content/routing policy merely because offline accuracy or provider price looks good; require outcome/quality impact at the appropriate evidence gate.

### Cost controls

| Control | Policy |
|---|---|
| Deterministic-first | never spend inference on exact code/SQL/library work |
| Precompute | reusable curriculum, mappings, exemplars, explanations and noninteractive generation are versioned offline when appropriate |
| Context minimization | send only the task + relevant learner-state snapshot |
| Escalation | second/stronger pass only for policy-defined hard/high-risk cases |
| Batch | auto-tagging, benchmark, recap/analytics generation may run offline/batch |
| Quota | token/audio/retry/concurrency allowances by plan/capability |
| Retry ceiling | one owner, bounded attempts; internal failures do not multiply charges |
| Feedback depth | reduce optional detail before scoring integrity |
| Fallback | save draft, reusable/basic explanation, delayed result, retry queue |
| Observability | cost is measured together with quality and verified learning outcome |

### Primary economics metrics

Track:

- `cost_per_active_learner`;
- `cost_per_evaluation`;
- `cost_per_successful_evaluation`;
- `model_escalation_rate`;
- `retry_cost_rate`;
- `audio_cost_per_speaking_attempt` where applicable;
- **`cost_per_verified_improvement`** — cost attributed to a learner loop that later produces governed independent improvement evidence.

Do not optimize only `cost/request`; cheap useless generation is waste.

### Cost-quality rules

- Do not increase cost/active learner without meaningful quality/outcome value.
- Do not lower a high-risk scorer below its benchmark-approved quality floor to meet quota.
- A premium plan may buy more depth/volume/latency priority, but free and premium share semantic truth and the minimum evaluation-quality floor.
- Optional coaching depth may degrade before scoring integrity.
- Every routing change uses canary/holdout where appropriate, rollback, cost attribution, and `GOVERNANCE.AuditTrail`.

### Cache, worker, and API reliability

- canonical state remains Postgres; cache/workflow/provider state never becomes entitlement/score/readiness truth;
- learner-data cache keys include subject scope + contract/version; no shared raw essay/audio cache key;
- async processing assumes at-least-once delivery with idempotent domain effects;
- every job has deadline, max attempts, backoff, replay/DLQ path as appropriate, trace/correlation ID, quota/cost attribution, and owner;
- API mutations are idempotent and expose semantic failures rather than provider exceptions.

## 5. Governance Engine (implement `GOVERNANCE.*`)

Governance controls automated evaluation without introducing a runtime human-scoring dependency. It is not a quality guarantee until benchmark corpus, thresholds, route configuration, and real runs exist.

### Sub-engines

| Engine | Implement | Description |
|---|---|---|
| Uncertainty/Confidence | `GOVERNANCE.ConfidenceScore` | route/result uncertainty signal; learner interpretation only after calibration |
| Gold-Standard Benchmark | `GOVERNANCE.GoldStandardBenchmark` | evaluate approved scorer routes against qualified reference data |
| Drift Detector | `GOVERNANCE.DriftDetection` | detect meaningful route/model performance change |
| Bias Monitor | `GOVERNANCE.BiasMonitoring` | inspect relevant slices only with adequate data/governance |
| Anti-Gaming | `GOVERNANCE.AntiGaming` | combine auditable integrity/exposure/similarity signals; detector alone is not proof |
| Audit Trail | `GOVERNANCE.AuditTrail` | route/model/rubric/config/release changes and benchmark provenance |

### Release workflow

```text
Candidate scorer route
  ↓
Rights/privacy/provider eligibility
  ↓
Gold benchmark suite
  - criterion agreement
  - task agreement
  - ±0.5 agreement where applicable
  - ordinal agreement metric
  - MAE/median absolute error as descriptive metrics
  - repeated-run stability
  - task/proficiency-region error
  - confidence/uncertainty calibration
  - regression versus promoted route
  ↓
Cost + latency profile
  ↓
Release gate
  ↓
Canary/controlled promotion
  ↓
Production monitoring + rollback
```

No single aggregate MAE threshold proves scorer validity.

### Offline reference data is not runtime human review

Qualified examiner-rated data may be used for benchmark/calibration if rights, provenance, sample design, privacy, and integrity are approved. That keeps the learner-facing runtime automated while preserving an external quality reference.

An AI-generated benchmark cannot be the sole gold validation of the same AI/scorer class.

### Re-evaluation and disputes

- preserve the original result and provenance;
- rerun through a governed route when policy permits;
- record the new result/version/status explicitly;
- never manually edit the numeric score in place;
- learner-facing history explains superseded/re-evaluated state without fabricating certainty.

### Governance metrics

Thresholds remain inactive until approved evidence exists. Candidate metric families include:

- criterion/task exact and within-tolerance agreement;
- ordinal agreement;
- absolute error distribution;
- repeated-run stability;
- limited/insufficient-evidence rate;
- calibration of uncertainty versus observed error;
- drift/regression by task/proficiency region;
- integrity false-positive rate;
- cost and escalation rate at equal quality.
